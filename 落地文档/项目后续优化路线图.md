## 一、本次重规划结论

项目已经完成了安全运行基线、AI 第一版评测基线、P0 记忆与工具路由修复，以及 P1 向量隔离、检索审计和完整清空会话的代码与单元测试。后续工作的重点不再是“继续增加记忆层或 RAG 组件”，而是先把现有记忆系统的契约修正一致，再验证、观测和优化。

当前最重要的判断是：

1. **MySQL 原始对话历史的归属隔离已完成并部署**。`conversations` 增加可空 `user_id`，新会话写入当前用户，读取、写入、清空和摘要变更统一校验 `userId + conversationId`；历史 `user_id = NULL` 会话保持不可读写，不自动猜测归属。
2. **同一条回复重复写入两份对话向量的代码路径已消除并部署**。`chatWithMemory` 的直接写入已删除，唯一写入链为 `saveMessagePair -> VectorSaveEvent -> MemoryEventListener`，并增加稳定文档 ID 和 SQLite 唯一索引。
3. **“清空会话”已完成并部署**。清空链路同步处理 MySQL 消息、当前用户的 SQLite 对话向量和 Session 状态，成功后再轮换会话 ID；前端只在后端成功后清空界面，公共知识库不受影响；生产端到端验证已通过。
4. **滚动摘要与 system 提示词的通用构建链路已完成统一**。业务提示词、RAG 和摘要会合并为唯一 system 消息，并在截断后保留；正式记忆入口已经接入该链路。
5. **入口记忆契约已经固定**。`/api/ai/chat/stream` 和 `/api/care/qa` 是正式持久化记忆入口；`/api/ai/chat` 和 `/api/ai/chat-with-tools` 明确定位为单轮兼容入口；旧 `AgentService` 与 `MessageRouter` 未接入 Web HTTP 主链路，保留为废弃候选。
6. **阶段 2.1 已完成 Web 正式入口的 RAG 检索接线，但真实知识、受控只读明细和 `Recall@K` 仍未完成**。`/api/ai/chat/stream` 已按真实 `userId + conversationId` 检索公共知识库与历史对话，`/api/care/qa` 复用统一 `RagContextService`；`/api/ai/chat` 与工具兼容入口继续按契约不执行 RAG。线上公共知识库目前仍只有测试种子，因此尚不能可靠计算 `Recall@K`。
7. **安全剩余项、数据增长、向量检索性能和工程清理仍然存在**，但不应在记忆语义统一前混入同一次修改。

因此，新版执行顺序调整为：

**先统一记忆契约和安全隔离，再完成回归验证与部署，然后补 RAG 可观测性，最后才做检索增强、UI 收敛和工程清理。**

## 二、优先级定义

| 级别 | 定义 | 处理原则 |
| --- | --- | --- |
| P0 | 用户隔离、安全暴露、数据损坏或生产上线阻塞问题 | 先修复并验证，不允许带着问题进入下一阶段 |
| P1 | 记忆正确性、回归风险、关键运维和可验证性 | 在 P0 完成后按依赖顺序处理 |
| P2 | 性能、成本、数据生命周期、工程维护和可观测性 | 在有稳定指标后优化，避免只凭感觉改架构 |
| P3 | UI 体验、产品范围收敛和非阻塞文档整理 | 放在核心链路稳定之后 |

推进规则：

1. 每一阶段只解决一类问题，保持改动小而可回滚。
2. 所有 AI 效果变化都必须与同一份评测题库比较。
3. 对疑似废弃代码先确认调用关系，再删除或标注。
4. 不把密钥轮换、限流、UI 改版和 RAG 改造混入同一次提交。
5. 不以 README 中的目标描述代替源码和运行结果。
6. 不伪造 `Recall@K`、引用命中率或人工评审结论。
7. 生产修改必须先有备份、验证和回滚路径。

## 五、新版分批路线

### 阶段 0：统一记忆契约与隔离语义

#### 目标

在继续评测和部署前，先让所有记忆相关代码、数据和文档对“谁的记忆、何时写入、怎样清空、摘要怎样生效”形成同一套契约。

#### 0.1 补齐 MySQL 对话归属

当前状态：**代码和自动化验证已完成并纳入本次交付，尚未部署。**

- 不同用户之间不会串记忆。
- `Recall@K`、答案正确率和引用命中率相比基线有提升。
- 多轮对话中的实体、时间和结论保持一致。

---

#### 第四批：UI 与产品范围收敛

#### 目标

先做减法，再改进视觉和交互，让用户快速理解核心价值。

#### 主要任务

- 明确一条核心用户路径：
  `用户提问 -> 记忆检索 -> 工具调用 -> 给出有依据的答案`。
- 下线旧入口、未完成功能和重复导航。
- 优先简化规模过大的静态页面，例如社区页和时光轴页。
- 抽取公共鉴权、API 请求、Toast、错误处理和加载状态。
- 短期保留现有静态页面结构，先降低重复代码，再评估是否引入前端框架。
- 统一移动端和桌面端的核心操作、信息层级和反馈状态。

#### 交付物

- 核心页面和功能保留清单。
- 旧功能下线清单。
- 公共前端模块。
- UI 简化和响应式改版结果。

#### 验收标准

- 核心路径入口更短。
- 页面不再同时展示大量同级功能和操作。
- 移动端与桌面端均无重叠、溢出或主要操作被遮挡。

---

#### 第五批：工程清理与可观测

#### 目标

降低长期维护成本，并为线上运行提供基础可观测能力。

#### 主要任务

- 确认 `AgentService`、`MessageRouter` 等旧链路是否确实废弃，再决定删除或标注。
- 统一 `@Tool` 与 `BaseTool` 的数量口径和文档说明。
- 拆分过大的服务类和控制器。
- 统一 HTTP 客户端、超时、重试和异常处理。
- 统一 API 返回结构和错误码。
- 对用户消息、工具参数和异常信息进行日志脱敏。
- 接入 Actuator、健康检查和基础运行指标。
- 补充工具注册、鉴权、文件上传、记忆隔离和 RAG 检索测试。

#### 交付物

- 死代码处理结论。
- 统一后的 HTTP 与异常处理方式。
- 健康检查和基础监控。
- 核心模块测试集。

#### 验收标准

- 文档和运行时工具数量一致。
- 关键链路具备自动化测试。
- 线上可观察请求、工具、线程池和外部服务状态。

### 四、部署与域名建议

使用域名不代表自动安全，完整上线流程至少包括：

1. 注册域名并配置 DNS。
2. 配置 HTTPS 证书。
3. 使用反向代理转发应用端口。
4. 不在公网直接暴露应用管理端口、数据库端口和调试端口。
5. 增加登录失败限制、接口限流和基础 WAF 或 CDN 防护。
6. 定期轮换密钥并检查依赖漏洞。
7. 根据服务器所在地和接入商要求处理 ICP 备案及其他必要备案。

如果服务器位于中国大陆，网站通常需要 ICP 备案；境外服务器一般不要求国内 ICP 备案，但仍需遵守服务商和当地法规。具体以实际部署区域和接入商要求为准。

---

### 五、推荐执行顺序

1. 安全修复与密钥轮换。
2. 构建、启动和鉴权基线。
3. AI 评测集和准确率基线。
4. 记忆分层与用户隔离。
5. RAG 召回、重排、压缩和引用。
6. UI 和产品范围收敛。
7. 旧链路、死代码和工程结构清理。
8. 域名、HTTPS、备案、限流和反滥用。

---

### 六、需要确认的事项

1. 服务器部署在中国大陆还是境外，决定备案和网络防护方案。
2. 哪些业务模块属于核心范围，哪些可以正式下线。
3. `AgentService` 和 `MessageRouter` 是否继续保留。
4. 外部服务密钥的轮换负责人和完成时间。
5. 30 到 50 条评测问题由业务方提供，还是先由开发侧生成初稿后评审。
6. 评测优化优先级是准确率、响应速度还是调用成本。
