## 一、本次重规划结论

项目已经完成了安全运行基线、AI 第一版评测基线、P0 记忆与工具路由修复，以及 P1 向量隔离和检索审计的代码与单元测试。后续工作的重点不再是“继续增加记忆层或 RAG 组件”，而是先把现有记忆系统的契约修正一致，再验证、观测和优化。

当前最重要的判断是：

1. **MySQL 原始对话历史还没有用户归属隔离**。`conversations` 和 `messages` 没有 `user_id`，读取只依赖 `conversationId`；真正完成 `userId + conversationId` 双条件隔离的是 SQLite 对话向量。
2. **同一条回复可能重复写入两份对话向量**。`saveMessagePair` 已经发布向量事件，`chatWithMemory` 又直接调用一次向量保存。
3. **“清空会话”不是完整语义**。当前没有同时清理 MySQL 消息、SQLite 向量和 Session 会话 ID，前端也只清空 DOM。
4. **滚动摘要可能被系统提示词遮蔽**。长对话被窗口截断后，早先事实可能无法进入提示词。
5. **各对话入口的记忆能力不一致**。`/api/ai/chat/stream` 和 `/api/care/qa` 有较完整记忆链路，`/api/ai/chat` 只做单次 RAG，`/api/ai/chat-with-tools` 不接入持久化多轮记忆。
6. **RAG 审计数据已经具备基础，但还缺受控只读明细接口**，因此 `Recall@K` 仍不能可靠计算。
7. **安全剩余项、数据增长、向量检索性能和工程清理仍然存在**，但不应在记忆语义统一前混入同一次修改。

因此，新版执行顺序调整为：

**先统一记忆契约和安全隔离，再完成回归验证与部署，然后补 RAG 可观测性，最后才做检索增强、UI 收敛和工程清理。**

## 二、优先级定义

| 级别 | 定义 | 处理原则 |
| --- | --- | --- |
| P0 | 用户隔离、安全暴露、数据损坏或生产上线阻塞问题 | 先修复并验证，不允许带着问题进入下一阶段 |
| P1 | 记忆正确性、回归风险、关键运维和可验证性 | 在 P0 完成后按依赖顺序处理 |
| P2 | 性能、成本、数据生命周期、工程维护和可观测性 | 在有稳定指标后优化，避免只凭感觉改架构 |
| P3 | UI 体验、产品范围收敛和非阻塞文档整理 | 放在核心链路稳定之后 |

推进规则：

1. 每一阶段只解决一类问题，保持改动小而可回滚。
2. 所有 AI 效果变化都必须与同一份评测题库比较。
3. 对疑似废弃代码先确认调用关系，再删除或标注。
4. 不把密钥轮换、限流、UI 改版和 RAG 改造混入同一次提交。
5. 不以 README 中的目标描述代替源码和运行结果。
6. 不伪造 `Recall@K`、引用命中率或人工评审结论。
7. 生产修改必须先有备份、验证和回滚路径。

## 五、新版分批路线

### 阶段 0：统一记忆契约与隔离语义

#### 目标

在继续评测和部署前，先让所有记忆相关代码、数据和文档对“谁的记忆、何时写入、怎样清空、摘要怎样生效”形成同一套契约。

#### 0.1 补齐 MySQL 对话归属

任务：

- 为 `conversations` 增加 `userId` 归属，或建立等价的会话归属表。
- 新会话创建时写入当前登录用户身份。
- 历史读取、消息写入和清空操作统一校验 `userId + conversationId`。
- 对所有调用方更新接口和参数传递，禁止继续使用仅按 `conversationId` 读取的生产路径。
- 对历史无归属数据制定迁移策略：可确认归属则回填，无法确认则隔离、归档或标记不可读取，不能猜测归属。
- 增加跨用户读取、错误会话 ID、未登录访问和旧数据访问测试。

验收：

- 用户 A 无法通过用户 B 的 `conversationId` 读取历史或写入消息。
- 数据库迁移、回滚和新会话创建均有自动化测试。
- README、设计文档和代码对隔离范围的描述一致。

#### 0.2 消除重复向量写入

任务：

- 删除 `chatWithMemory` 中重复的 `asyncSaveVector` 调用。
- 保留 `saveMessagePair -> VectorSaveEvent -> MemoryEventListener` 的唯一写入链。
- 增加幂等或去重键，至少避免同一轮消息对重复入库。
- 检查其他调用方是否绕过事件链直接写向量。

验收：

- 同一轮对话只产生一份可检索的对话向量。
- 重复事务重试不会无限增加向量数量。
- 有测试能断言向量数量和消息对数量一致。

#### 0.3 重做“清空会话”完整流程

任务：

- 增加后端清空会话语义，统一处理 MySQL 消息、SQLite 对话向量和 Session 状态。
- 清空后轮换或重新生成 `conversationId`，避免后续消息继续写入旧会话。
- 前端等待后端成功后再清 DOM，失败时保留提示和可重试状态。
- 明确公共知识库向量不会被用户清空。
- 增加重复点击、并发清空和失败回滚测试。

验收：

- 清空后刷新页面、重新读取历史和再次检索都不会召回该会话旧内容。
- 公共知识库仍可正常使用。
- 用户无法通过旧 `conversationId` 继续追加消息。

#### 0.4 统一摘要与系统提示词

任务：

- 当调用方已有系统提示词时，将滚动摘要合并进 system 消息，而不是直接跳过。
- 明确提示词顺序：安全规则在前，业务规则随后，滚动摘要作为历史事实补充。
- 保证流式对话、护理问答和旧 Agent 链路使用同一套摘要读取规则。
- 增加长对话、摘要存在、系统提示词同时存在的回归测试。

验收：

- 长对话窗口截断后仍能保留实体、结论和未完成任务。
- 摘要不会覆盖安全规则或业务边界。
- 摘要读取行为在入口真值表中可解释。

#### 0.5 固定入口记忆真值表

任务：

- 为每个对话入口记录：是否读取 MySQL 历史、是否读取摘要、是否做 RAG、是否保存消息、是否保存向量。
- 对 `/api/ai/chat`、`/api/ai/chat-with-tools`、`MessageRouter` 和旧 `AgentService` 明确保留、改造或废弃结论。
- 让文档、接口和测试共享同一份入口语义。

验收：

- 任意入口都能回答“它有没有多轮记忆、会不会写向量、清空是否生效”。
- 没有入口继续依赖未定义的隐式会话状态。
- 测试覆盖每个保留入口的核心记忆行为。

#### 阶段 0 明确不做

- 不增加新的长期记忆层。
- 不更换模型、Embedding、TopK 或相似度阈值。
- 不引入 HNSW 或新的向量数据库。
- 不做 UI 改版。
- 不把密钥轮换和全局限流混入本阶段。

### 阶段 2：RAG 可观测性与召回指标

#### 目标

让评测侧能看到“回答到底命中了什么”，但不对公开用户暴露内部检索细节。

#### 主要任务

- 增加受控、只读、可审计的召回明细查询能力。
- 支持按 `traceId` 或受控会话标识查询命中的 `documentId`、`sourceId`、`origin` 和相似度。
- 不返回查询明文、文档正文、Cookie、密钥或完整用户隐私。
- 为接口增加角色、环境开关和访问审计。
- 将正式题库中的 `expectedSourceIds` 映射到真实来源 ID。
- 计算 `Recall@K` 和引用命中率，必要时再增加 Groundedness 口径。
- 在评测报告中保存计算口径、配置版本和原始 JSONL，确保可以离线重算。

#### 验收

- 每次保留入口的回答都能回溯到检索记录。
- `Recall@K` 和引用指标有可复现数据，不使用人工猜测值。
- 内部观测接口未登录、越权或非评测环境无法访问。

### 阶段 3：记忆生命周期与检索能力升级

#### 目标

在隔离和指标稳定后，处理数据增长、重复内容和检索能力问题。

#### 3.1 消息和摘要生命周期

- 定义保留期限、归档策略和删除策略。
- 摘要成功后归档或删除已压缩旧消息，避免 MySQL 持续膨胀。
- 增加摘要更新失败重试和幂等处理。
- 增加历史归档、恢复和删除测试。

#### 3.2 向量数据治理

- 为对话向量增加稳定去重键，例如消息对哈希或 `conversationId + documentId`。
- 知识库删除、帖子删除时同步清理对应公共向量。
- 增加历史孤儿向量扫描和清理任务。
- 明确对话向量、公共向量和审计日志各自的保留周期。

#### 3.3 Embedding 与检索性能

- 将 `embedBatch` 改为真正批量或受控并发调用。
- 在数据量达到明确阈值前不盲目替换向量存储。
- 当启动时间、内存占用或 P95 延迟超过预算时，再评估 HNSW 或 SQLite 向量扩展。
- 保留线性扫描作为对照路径或回退方案，直到新索引通过正确性和性能验证。

#### 3.4 检索质量增强

- 增加关键词检索与向量检索的混合召回。
- 增加重排，避免只按相似度直接拼接上下文。
- 增加只压缩表达、不改变事实、数字、时间和来源的上下文压缩。
- 回答保留可追溯引用。
- 记录命中资料、最终使用情况和最终引用之间的关系。

#### 验收

- MySQL 数据增长速度和存储成本可控。
- 删除内容不再被检索。
- `Recall@K`、回答质量和引用命中率相比阶段 2 有明确提升。
- P95 延迟和 Embedding 成本没有不可接受的回退。

### 阶段 4：安全剩余项与运维

#### 目标

把公开上线后的剩余安全和恢复能力收口。

#### 主要任务

- 在用户恢复密钥轮换后，轮换所有外部服务密钥并撤销旧密钥。
- 检查 Git 历史、旧构建产物、服务器日志和临时文件是否仍含历史凭据。
- 在 Nginx、网关或 WAF 层增加按 IP 和路径的限流，覆盖 AI、上传和登录等高风险入口。
- 为上传解析设置超时、并发隔离和必要的恶意文件扫描。

#### 验收标准

- 不同用户之间不会串记忆。
- `Recall@K`、答案正确率和引用命中率相比基线有提升。
- 多轮对话中的实体、时间和结论保持一致。

---

#### 第四批：UI 与产品范围收敛

#### 目标

先做减法，再改进视觉和交互，让用户快速理解核心价值。

#### 主要任务

- 明确一条核心用户路径：
  `用户提问 -> 记忆检索 -> 工具调用 -> 给出有依据的答案`。
- 下线旧入口、未完成功能和重复导航。
- 优先简化规模过大的静态页面，例如社区页和时光轴页。
- 抽取公共鉴权、API 请求、Toast、错误处理和加载状态。
- 短期保留现有静态页面结构，先降低重复代码，再评估是否引入前端框架。
- 统一移动端和桌面端的核心操作、信息层级和反馈状态。

#### 交付物

- 核心页面和功能保留清单。
- 旧功能下线清单。
- 公共前端模块。
- UI 简化和响应式改版结果。

#### 验收标准

- 核心路径入口更短。
- 页面不再同时展示大量同级功能和操作。
- 移动端与桌面端均无重叠、溢出或主要操作被遮挡。

---

#### 第五批：工程清理与可观测

#### 目标

降低长期维护成本，并为线上运行提供基础可观测能力。

#### 主要任务

- 确认 `AgentService`、`MessageRouter` 等旧链路是否确实废弃，再决定删除或标注。
- 统一 `@Tool` 与 `BaseTool` 的数量口径和文档说明。
- 拆分过大的服务类和控制器。
- 统一 HTTP 客户端、超时、重试和异常处理。
- 统一 API 返回结构和错误码。
- 对用户消息、工具参数和异常信息进行日志脱敏。
- 接入 Actuator、健康检查和基础运行指标。
- 补充工具注册、鉴权、文件上传、记忆隔离和 RAG 检索测试。

#### 交付物

- 死代码处理结论。
- 统一后的 HTTP 与异常处理方式。
- 健康检查和基础监控。
- 核心模块测试集。

#### 验收标准

- 文档和运行时工具数量一致。
- 关键链路具备自动化测试。
- 线上可观察请求、工具、线程池和外部服务状态。

### 四、部署与域名建议

使用域名不代表自动安全，完整上线流程至少包括：

1. 注册域名并配置 DNS。
2. 配置 HTTPS 证书。
3. 使用反向代理转发应用端口。
4. 不在公网直接暴露应用管理端口、数据库端口和调试端口。
5. 增加登录失败限制、接口限流和基础 WAF 或 CDN 防护。
6. 定期轮换密钥并检查依赖漏洞。
7. 根据服务器所在地和接入商要求处理 ICP 备案及其他必要备案。

如果服务器位于中国大陆，网站通常需要 ICP 备案；境外服务器一般不要求国内 ICP 备案，但仍需遵守服务商和当地法规。具体以实际部署区域和接入商要求为准。

---

### 五、推荐执行顺序

1. 安全修复与密钥轮换。
2. 构建、启动和鉴权基线。
3. AI 评测集和准确率基线。
4. 记忆分层与用户隔离。
5. RAG 召回、重排、压缩和引用。
6. UI 和产品范围收敛。
7. 旧链路、死代码和工程结构清理。
8. 域名、HTTPS、备案、限流和反滥用。

---

### 六、需要确认的事项

1. 服务器部署在中国大陆还是境外，决定备案和网络防护方案。
2. 哪些业务模块属于核心范围，哪些可以正式下线。
3. `AgentService` 和 `MessageRouter` 是否继续保留。
4. 外部服务密钥的轮换负责人和完成时间。
5. 30 到 50 条评测问题由业务方提供，还是先由开发侧生成初稿后评审。
6. 评测优化优先级是准确率、响应速度还是调用成本。
