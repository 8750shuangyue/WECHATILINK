# 项目后续优化路线图

> 整理日期：2026-09-11
>
> 文档定位：将近期项目评审、产品建议和工程分析整理为可执行的后续优化方案。
>
> 安全说明：本文不记录聊天中出现的账号、密码、公网地址、API Key 或其他敏感凭据。

---

## 一、总体结论

当前项目已经具备较完整的功能范围，包括 AI 对话、工具调用、护理、商城、社区、时间线、知识库和推送等模块，但现阶段的主要问题不是功能数量不足，而是：

1. 核心产品范围不够集中，部分旧功能和页面没有正式退出。
2. AI 回答准确度没有量化，缺少固定评测集和可比较指标。
3. 上下文记忆和 RAG 召回链路仍需系统化设计。
4. 公网部署、密钥管理和接口防护需要优先加固。
5. 前端页面和部分服务类规模较大，公共能力缺少抽取。
6. 自研 Agent 与 Spring AI 工具链并存，旧链路是否废弃尚未正式确认。
7. 自动化测试覆盖较少，无法为后续重构提供稳定保护。

后续优化的核心原则是：

**先安全、再评测准确率，然后优化记忆和 RAG，最后处理 UI、死代码和工程结构。**

---

## 二、优化原则

1. 准确率优先于功能数量。
2. 先收敛范围，再增加新能力。
3. 所有 AI 效果优化必须保留修改前基线。
4. 每一批改动保持可验证、可回滚，不把安全、AI、UI 混在同一次修改中。
5. 先复用现有 Spring Boot、Spring AI 和静态前端结构，不急于整体迁移技术栈。
6. 对疑似死代码先确认调用关系，再决定删除或标注废弃。
7. 不把密钥、公网地址、账号密码或完整用户输入写入文档、日志和仓库。

### 第一批：安全修复与运行基线

#### 目标

先消除直接暴露的安全风险，并建立后续改动所需的构建和运行基线。

#### 主要任务

- 检查当前 Git 改动，使用独立分支处理优化工作，建议分支名：
  `codex/optimization-foundation`。
- 将 `src/main/resources/application.properties` 中的真实密钥恢复为环境变量占位符。
- 真实本地配置只保留在已忽略的 `application-local.properties` 中。
- 盘点所有外部服务密钥，形成轮换清单。
- 收紧接口白名单、CORS、上传大小限制和文件类型校验。
- 检查 Session 鉴权、Cookie 和 CSRF 风险。
- 补充最小构建、启动、鉴权和文件上传验证。
- 部署侧单独处理域名、HTTPS、反向代理、端口关闭、限流和数据库网络隔离。

#### 交付物

- 无明文密钥的仓库配置。
- 密钥轮换清单。
- 安全风险清单。
- 可重复执行的构建、启动和最小鉴权验证结果。

#### 验收标准

- 仓库中不存在真实密钥。
- 本地通过环境变量或本地忽略文件正常启动。
- 未登录接口和公开资源边界清晰。
- 数据库和管理端口不直接暴露到公网。

### 第二批：建立 AI 评测基线

#### 目标

在没有量化基线之前，不继续大改提示词、模型和 RAG 链路。

#### 主要任务

- 建立 30 到 50 条真实评测问题，覆盖：
  - 植物识别与养护
  - 宠物护理与健康问答
  - 工具调用
  - 多轮对话
  - 知识库检索
  - 超出能力范围时的拒答
- 每条问题记录：
  - 标准答案或关键事实
  - 应该召回的资料来源
  - 是否应该调用工具
  - 允许的回答范围
  - 典型错误答案
- 建立统一评测入口，记录模型、提示词、RAG 配置和工具配置。
- 采用自动指标、模型评审和人工抽查组合评估。

#### 建议指标

| 指标 | 说明 |
|---|---|
| 答案正确率 | 关键事实与标准答案是否一致 |
| `Recall@K` | 正确资料是否进入前 K 个召回结果 |
| 引用命中率 | 回答是否能对应到正确资料来源 |
| Groundedness | 结论是否有检索内容或工具结果支撑 |
| 幻觉率 | 是否出现无依据事实、数字或结论 |
| 工具成功率 | 工具是否被正确选择并成功执行 |
| 记忆一致率 | 多轮对话中是否保持用户和对象信息一致 |
| P95 延迟 | 核心请求的端到端响应时间 |
| 单次成本 | 模型、Embedding 和外部服务的综合成本 |

#### 交付物

- 固定评测数据集。
- 可重复运行的评测脚本或测试入口。
- 第一版准确率和性能基线报告。

#### 验收标准

- 能明确回答当前准确率是多少。
- 每次改动后能对比提升或回退。
- 评测结果不会被单次主观体验替代。

#### 第一版基线结果

2026-10-01 已完成第一版正式基线：

- 请求记录 56 次，质量评分样本 52 个。
- 质量通过 47 个，质量通过率 `90.38%`。
- 关键事实覆盖率 `93.27%`，工具选择准确率 `87.50%`，拒答边界得分 `100.00%`。
- 多轮记忆最终轮 `0/4`，是当前最明确的质量缺口。
- `tool-006` 的一次重复运行漏调 `triageSymptoms`，回答事实正确但工具选择失败。
- 总延迟均值约 `21.24 秒`，P95 `58.42 秒`。
- 公开 HTTP 接口没有返回内部 RAG 召回明细，`Recall@K` 仍不可计算，禁止用人工猜测值填充。

第二批的后续动作不是继续扩大题库，而是先把这两个已确认的问题纳入第三批：

1. 修复多轮会话中的实体、时间和对象信息保持。
2. 修正 `tool-006` 对应场景的工具路由稳定性。
3. 为 RAG 增加受控、只读、可审计的检索观测数据，再补齐 `Recall@K` 和引用指标。

### 第三批：记忆与 RAG 优化

#### 目标

解决多轮记忆错乱、检索命中不稳定和回答缺少依据的问题。

#### 记忆分层

1. 最近对话：保留原始消息，负责当前语境。
2. 会话摘要：压缩较早历史，但保留实体、结论和未完成任务。
3. 长期记忆：用户、宠物、植物、偏好和护理记录使用结构化字段保存。

#### RAG 链路

完整链路建议为：

`文档切分 -> 元数据标记 -> 索引 -> 查询改写 -> 混合召回 -> 重排 -> 上下文压缩 -> 生成回答 -> 引用与评估`

#### 主要任务

- 每个向量切片携带 `userId`、`conversationId`、来源、类型和时间等元数据。
- 先做用户与会话隔离，再做相似度召回，避免跨用户串记忆。
- 增加关键词检索和向量检索的混合召回。
- 增加重排，避免只按向量相似度直接拼接上下文。
- 上下文压缩只压缩表达，不修改事实、数字、时间和来源。
- 回答保留可追溯引用。
- 记录每次检索命中的资料、相似度和最终使用情况。
- 数据量增长后替换当前全量内存余弦扫描，可优先评估项目已引入的 HNSW 依赖或专用向量存储。

#### 交付物

- 新的记忆分层设计。
- RAG 元数据和隔离规则。
- 检索日志与引用机制。
- 优化前后评测对比。

#### 验收标准

- 不同用户之间不会串记忆。
- `Recall@K`、答案正确率和引用命中率相比基线有提升。
- 多轮对话中的实体、时间和结论保持一致。

### 第四批：UI 与产品范围收敛

#### 目标

先做减法，再改进视觉和交互，让用户快速理解核心价值。

#### 主要任务

- 明确一条核心用户路径：
  `用户提问 -> 记忆检索 -> 工具调用 -> 给出有依据的答案`。
- 下线旧入口、未完成功能和重复导航。
- 优先简化规模过大的静态页面，例如社区页和时光轴页。
- 抽取公共鉴权、API 请求、Toast、错误处理和加载状态。
- 短期保留现有静态页面结构，先降低重复代码，再评估是否引入前端框架。
- 统一移动端和桌面端的核心操作、信息层级和反馈状态。

#### 交付物

- 核心页面和功能保留清单。
- 旧功能下线清单。
- 公共前端模块。
- UI 简化和响应式改版结果。

#### 验收标准

- 核心路径入口更短。
- 页面不再同时展示大量同级功能和操作。
- 移动端与桌面端均无重叠、溢出或主要操作被遮挡。

## 四、部署与域名建议

使用域名不代表自动安全，完整上线流程至少包括：

1. 注册域名并配置 DNS。
2. 配置 HTTPS 证书。
3. 使用反向代理转发应用端口。
4. 不在公网直接暴露应用管理端口、数据库端口和调试端口。
5. 增加登录失败限制、接口限流和基础 WAF 或 CDN 防护。
6. 定期轮换密钥并检查依赖漏洞。
7. 根据服务器所在地和接入商要求处理 ICP 备案及其他必要备案。

如果服务器位于中国大陆，网站通常需要 ICP 备案；境外服务器一般不要求国内 ICP 备案，但仍需遵守服务商和当地法规。具体以实际部署区域和接入商要求为准。
