# 备份保留、新鲜度与恢复策略

> 文档日期：2026-10-10
> 适用范围：`ilink_chat` MySQL、`rag_knowledge.sqlite`、发布 JAR 和生产配置
> 执行脚本：`scripts/check-backup-retention.ps1`、`scripts/test-stage3-2-backup-restore.ps1`
> 当前服务器：只读检查通过，阶段 3.2 首次治理前回滚包完整

## 一、目标

本策略用于保证生产数据在发布、治理和故障恢复场景下具备以下能力：

- 每次发布或高风险数据变更前都有完整回滚包。
- 可以判断最近备份是否完整、可用且不过期。
- MySQL 和 SQLite 都具备可验证的恢复输入。
- 保留期限明确，避免无限占用磁盘，也避免提前删除唯一可用备份。
- 备份异常能够在人工执行检查时产生明确告警。

本策略当前不包含外部告警平台接入，也不自动授权删除备份。检查脚本只做只读盘点、判定和报告生成。

## 二、备份对象

| 对象 | 必需性 | 说明 |
| --- | --- | --- |
| `demo-0.0.1-SNAPSHOT.jar` | 必需 | 可回滚应用版本 |
| `ilink_chat.sql` | 必需 | MySQL 逻辑备份 |
| `ilink_chat.sql.sha256` | 必需 | MySQL 备份哈希 |
| `rag_knowledge.sqlite` | 必需 | SQLite 一致性副本 |
| `rag_knowledge.sqlite.sha256` | 必需 | SQLite 备份哈希 |
| `production.conf` | 必需 | systemd 生产环境配置副本 |
| `production.conf.sha256` | 必需 | 生产配置哈希 |
| `jar.sha256` | 必需 | JAR 哈希 |

备份目录不得包含账号密码明文、API Key、Cookie、Session 或其他运行凭据。需要恢复的敏感配置应由服务器权限和受控运维流程保护。

## 三、目录与命名

默认根目录：

```text
/opt/ilink/backups
```

备份目录和快照目录名必须以本地时间开头：

```text
YYYYMMDD-HHMMSS-<用途>
```

示例：

```text
20261010-141347-stage3-2
```

当前阶段 3.2 回滚包：

```text
/opt/ilink/backups/20261010-141347-stage3-2
```

没有可解析时间前缀的历史目录会回退到目录修改时间，仅用于容错，不应作为新备份标准。

## 四、保留策略

| 类型 | 保留期限 | 说明 |
| --- | ---: | --- |
| 当前发布回滚包 | `90` 天 | 阶段 3.2 和高风险发布必须优先保留 |
| 每日包 | `14` 天 | 覆盖近期日常误操作和数据增长 |
| 每周包 | `8` 周 | 每周保留一个最新完整包 |
| 每月包 | `6` 个月 | 每月保留一个最新完整包 |

保留原则：

1. 当前发布回滚包不因每日轮转而提前删除。
2. 每周包和每月包优先保留最新完整包。
3. 检查脚本不会自动删除任何文件。
4. 删除前必须确认至少存在一个更新的完整、校验通过的回滚包。
5. 缺文件或校验失败的历史临时包不能被当作新恢复点。
6. 删除动作应由人工执行并记录原因，不能由自动治理任务顺带完成。

## 五、新鲜度与告警

检查脚本默认阈值：

| 条件 | 级别 | 处理要求 |
| --- | --- | --- |
| 最新完整包年龄不超过 `26` 小时 | 不告警 | 正常 |
| 最新完整包超过 `26` 小时 | `WARNING` | 当日检查并补备份 |
| 最新完整包超过 `50` 小时 | `CRITICAL` | 停止高风险发布和治理，立即补备份并排查 |
| 当前回滚包缺失 | `CRITICAL` | 停止继续治理，查找或重建回滚包 |
| 当前回滚包校验失败 | `CRITICAL` | 不可用于回滚，立即生成新包 |
| 历史临时包缺文件 | `WARNING` | 记录，不扩大误报 |
| 历史临时包哈希失败 | `CRITICAL` | 隔离该包并排查来源 |
| MySQL dump 缺少结束标记 | `CRITICAL` | 备份可能不完整 |
| SQLite 完整性不是 `ok` | `CRITICAL` | 备份不可用于恢复 |

退出码：

- `0`：`OK` 或 `WARNING`。
- `1`：存在 `CRITICAL`。

## 六、完整性检查

检查脚本会执行：

- 必需文件是否存在。
- 每个 `.sha256` 文件格式是否合法。
- 哈希目标是否存在。
- SHA-256 是否一致。
- MySQL dump 最后 4096 字节是否包含 `Dump completed`。
- SQLite 是否可只读打开。
- SQLite `PRAGMA integrity_check` 是否返回 `ok`。
- 当前发布回滚包是否仍存在且完整。
- 备份年龄、保留原因和磁盘容量。

执行命令：

```powershell
pwsh -NoProfile -Command "& '.\scripts\check-backup-retention.ps1'"
```

报告输出：

```text
.runtime-reports/stage3-2-backup-retention-<timestamp>.json
.runtime-reports/stage3-2-backup-retention-<timestamp>.md
```

## 八、调度策略

当前阶段 3.2 已建立检查、保留和恢复门禁，但自动生成每日、每周、每月完整备份的定时任务尚未纳入阶段 3.2 代码。

后续实施每日自动备份时，建议：

- 在每日 03:30 治理任务前完成备份。
- 每天生成一次每日包。
- 每周保留一个最新完整包。
- 每月保留一个最新完整包。
- 每次发布另建受保护的发布回滚包。
- 备份完成后自动运行完整性检查和新鲜度检查。

在自动备份未落地前，人工检查不能停止。首次治理或下一次高风险发布前，必须确认存在 50 小时内生成的完整、校验通过的回滚包。

## 九、异常处理

### 9.1 `WARNING`

1. 查看报告中的包名、缺失文件、年龄和保留原因。
2. 区分历史临时包和当前发布回滚包。
3. 如果最新完整包超过 26 小时，在服务正常时立即补备份。
4. 补备份后重新运行检查脚本。

### 9.2 `CRITICAL`

1. 暂停发布、数据治理和任何批量删除。
2. 保留现有备份、日志和数据库文件。
3. 确认是文件缺失、哈希失败、dump 不完整还是 SQLite 损坏。
4. 立即生成新备份，但不要覆盖异常包。
5. 确认新包完整并通过恢复演练后，再决定是否继续发布或治理。
6. 如果恢复点是唯一可用副本，不要删除，也不要直接在生产目录上试验恢复。

## 十、恢复原则

恢复顺序：

1. 关闭应用或治理任务。
2. 备份当前现场文件，避免覆盖证据。
3. 恢复 JAR 和生产配置。
4. 启动服务并验证基础可用性。
5. 仅在 SQLite 损坏或错误删除时恢复 SQLite。
6. 仅在 MySQL 损坏或错误删除时恢复 MySQL。
7. 恢复后执行完整性检查、向量数量核对和功能回归。

MySQL 恢复会丢失备份点之后的新对话、帖子、知识和其他业务写入。执行前必须明确数据丢失范围。
