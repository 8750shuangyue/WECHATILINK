# 阶段 3.2 生产发布与回滚清单

> 文档日期：2026-10-10
> 适用范围：向量数据治理、保留周期、删除一致性、孤儿向量清理
> 当前代码与生产基线：`main` 分支提交 `1d12cb9`
> 发布原则：先部署代码并保持治理关闭，完成备份和只读盘点后，再显式开启定时治理

## 一、发布范围

阶段 3.2 包含以下能力：

- 清理阶段 0.2 之前产生的历史重复对话向量。
- 按来源整体替换公共知识向量，并支持知识删除时同步清理。
- 在社区帖子删除时同步清理对应公共向量。
- 清理没有业务记录的孤儿公共向量。
- 对对话向量和 RAG 审计日志执行保留周期清理。
- 治理失败时通过事务回滚，并保留失败日志。

本次发布不包含：

- 真实业务知识导入。
- `expectedSourceIds` 映射。
- 40 题复测和 `Recall@K` 计算。
- 外部监控告警平台接入。

## 二、默认参数与执行时间

生产默认参数如下：

| 配置 | 当前值 | 作用 |
|---|---:|---|
| `app.data-governance.enabled` | `false` | 自动治理总开关，首次部署保持关闭 |
| `chat.vectorstore.duplicate-cleanup-cron` | `0 0 4 * * *` | 每天 04:00 清理重复对话向量 |
| `chat.vectorstore.conversation-retention-days` | `90` | 对话向量保留 90 天 |
| `chat.vectorstore.conversation-retention-cleanup-cron` | `0 15 4 * * *` | 每天 04:15 清理过期对话向量 |
| `rag.retention.retrieval-log-days` | `180` | RAG 检索日志保留 180 天 |
| `rag.retention.observability-access-log-days` | `180` | 检索观测访问日志保留 180 天 |
| `rag.retention.cleanup-cron` | `0 30 4 * * *` | 每天 04:30 清理过期审计日志 |
| `community.vector-governance.orphan-cleanup-cron` | `0 30 3 * * *` | 每天 03:30 清理孤儿社区向量 |

执行时间以服务器时区为准。部署前必须执行：

```bash
timedatectl
date
```

确认服务器时区与业务预期一致。

## 四、备份步骤

以下命令在服务器执行。不要把数据库密码写入脚本、命令历史或文档。

```bash
STAMP="$(date +%Y%m%d-%H%M%S)"
BACKUP="/opt/ilink/backups/${STAMP}-stage3-2"
mkdir -p "$BACKUP"
chmod 700 "$BACKUP"

cd /opt/ilink
cp demo-0.0.1-SNAPSHOT.jar "$BACKUP/demo-0.0.1-SNAPSHOT.jar"
sha256sum demo-0.0.1-SNAPSHOT.jar > "$BACKUP/jar.sha256"
sha256sum /etc/systemd/system/ilink.service.d/production.conf \
  > "$BACKUP/production.conf.sha256"
```

备份 MySQL：

```bash
read -rsp "MySQL password: " MYSQL_PASSWORD
echo
mysqldump -uroot -p"$MYSQL_PASSWORD" \
  --single-transaction \
  --routines \
  --triggers \
  ilink_chat > "$BACKUP/ilink_chat.sql"
unset MYSQL_PASSWORD

test -s "$BACKUP/ilink_chat.sql"
tail -n 5 "$BACKUP/ilink_chat.sql" | grep -q "Dump completed"
sha256sum "$BACKUP/ilink_chat.sql" > "$BACKUP/ilink_chat.sql.sha256"
```

备份 SQLite：

```bash
sqlite3 /opt/ilink/rag_knowledge.sqlite \
  ".backup '$BACKUP/rag_knowledge.sqlite'"

sqlite3 "$BACKUP/rag_knowledge.sqlite" "PRAGMA integrity_check;"
sha256sum "$BACKUP/rag_knowledge.sqlite" \
  > "$BACKUP/rag_knowledge.sqlite.sha256"
```

`PRAGMA integrity_check` 必须返回 `ok`。返回其他结果时停止发布。

当前生产服务器未安装 `sqlite3` CLI，但已有 Python 3.10 和标准库 `sqlite3`。在执行第 5 节盘点前，可用 Python 标准库完成等价的在线备份、完整性检查和只读查询，不要为此临时安装新软件包。

## 五、发布前只读盘点

### 5.1 向量总量与分类

```bash
sqlite3 -header -column /opt/ilink/rag_knowledge.sqlite <<'SQL'
SELECT
  CASE
    WHEN conversation_id IS NOT NULL
      AND conversation_id <> ''
      AND (source_id IS NULL OR source_id = '')
      THEN 'conversation'
    WHEN source_id IS NOT NULL AND source_id <> ''
      THEN 'public'
    ELSE 'other'
  END AS kind,
  COUNT(*) AS row_count
FROM vector_store
GROUP BY kind
ORDER BY kind;
SQL
```

### 5.2 公共来源清单

```bash
sqlite3 -header -column /opt/ilink/rag_knowledge.sqlite <<'SQL'
SELECT
  source_id,
  COUNT(*) AS chunk_count,
  MIN(timestamp) AS first_seen,
  MAX(timestamp) AS last_seen
FROM vector_store
WHERE source_id IS NOT NULL
  AND source_id <> ''
  AND (conversation_id IS NULL OR conversation_id = '')
GROUP BY source_id
ORDER BY source_id;
SQL
```

记录所有 `post_` 来源。若 `post_1`、`post_2` 仍然对应现存帖子，它们不是孤儿。

### 5.3 重复对话向量估算

```bash
sqlite3 -header -column /opt/ilink/rag_knowledge.sqlite <<'SQL'
SELECT
  COUNT(*) AS duplicate_groups,
  COALESCE(SUM(c - 1), 0) AS estimated_duplicate_rows
FROM (
  SELECT COUNT(*) AS c
  FROM vector_store
  WHERE conversation_id IS NOT NULL
    AND conversation_id <> ''
    AND (source_id IS NULL OR source_id = '')
  GROUP BY COALESCE(user_id, ''), conversation_id, content
  HAVING COUNT(*) > 1
);
SQL
```

这是保守估算，不是完整治理 dry-run。正式清理仍以阶段 3.2 代码内的稳定文档 ID 分组结果为准。

### 5.4 过期数据估算

```bash
sqlite3 -header -column /opt/ilink/rag_knowledge.sqlite <<'SQL'
SELECT 'conversation_90d' AS bucket, COUNT(*) AS row_count
FROM vector_store
WHERE conversation_id IS NOT NULL
  AND conversation_id <> ''
  AND (source_id IS NULL OR source_id = '')
  AND datetime(timestamp) < datetime('now', 'localtime', '-90 days')
UNION ALL
SELECT 'retrieval_log_180d', COUNT(*)
FROM rag_retrieval_log
WHERE datetime(created_at) < datetime('now', 'localtime', '-180 days')
UNION ALL
SELECT 'observability_access_180d', COUNT(*)
FROM rag_observability_access_log
WHERE datetime(created_at) < datetime('now', 'localtime', '-180 days');
SQL
```

### 5.5 SQLite 结构检查

```bash
sqlite3 /opt/ilink/rag_knowledge.sqlite "PRAGMA integrity_check;"
sqlite3 /opt/ilink/rag_knowledge.sqlite \
  "SELECT name FROM sqlite_master WHERE type = 'index' AND name = 'uk_vector_store_document_id';"
```

第二条命令必须返回唯一索引名称。

### 5.6 MySQL 帖子对应关系

```bash
read -rsp "MySQL password: " MYSQL_PASSWORD
echo
mysql -uroot -p"$MYSQL_PASSWORD" ilink_chat \
  -e "SELECT COUNT(*) AS posts FROM community_posts;
      SELECT id, title FROM community_posts WHERE id IN (1, 2) ORDER BY id;" \
  > "$BACKUP/posts_count.txt"
unset MYSQL_PASSWORD
```

将 5.2 中的 `post_` 来源与 `community_posts` 的帖子 ID 逐一对照，确认没有把现存帖子误判为孤儿。生产表的真实名称是 `community_posts`，不是 `posts`。

## 七、首次开启治理

完成备份、只读盘点和 6.3 基础验证后，在维护窗口执行：

1. 编辑 `/etc/systemd/system/ilink.service.d/production.conf`。
2. 将 `APP_DATA_GOVERNANCE_ENABLED` 改为 `true`。
3. 只检查开关，不输出其他密钥配置。
4. 重新加载并重启。

```bash
sudo systemctl daemon-reload
sudo systemctl restart ilink
sleep 60
```

不要为了提前验证而随意把所有 cron 改成每分钟。先让任务按正式时间运行一次，保留真实执行记录。

## 九、回滚步骤

### 9.1 先关闭治理

```bash
sudo systemctl stop ilink
sudo systemctl daemon-reload
```

将 `APP_DATA_GOVERNANCE_ENABLED` 改回 `false`。

### 9.2 恢复旧 JAR

```bash
BACKUP="/opt/ilink/backups/<发布时备份目录>"
cp "$BACKUP/demo-0.0.1-SNAPSHOT.jar" \
  /opt/ilink/demo-0.0.1-SNAPSHOT.jar
chown admin:admin /opt/ilink/demo-0.0.1-SNAPSHOT.jar
sudo systemctl start ilink
```

### 9.3 仅在数据确实损坏时恢复 SQLite

```bash
sudo systemctl stop ilink
cp /opt/ilink/rag_knowledge.sqlite \
  /opt/ilink/rag_knowledge.sqlite.before-rollback
cp "$BACKUP/rag_knowledge.sqlite" /opt/ilink/rag_knowledge.sqlite
chown admin:admin /opt/ilink/rag_knowledge.sqlite
sqlite3 /opt/ilink/rag_knowledge.sqlite "PRAGMA integrity_check;"
sudo systemctl start ilink
```

### 9.4 MySQL 恢复原则

阶段 3.2 预计不需要恢复 MySQL。MySQL dump 是灾难恢复后备。

恢复 MySQL 会丢失备份点之后的新对话、新帖子和新知识。只有确认 MySQL 发生损坏或错误删除时才执行，并且必须同时评估数据丢失范围。

## 十、当前风险与后续改进

| 风险 | 当前处理 | 后续项 |
|---|---|---|
| 首次部署可能自动清数据 | 总开关默认关闭，验证后再开启 | 保持运维门禁 |
| 重复向量清理是全量扫描 | 先设置数据量门禁 | 增加分批扫描和进度日志 |
| 孤儿向量清理是全量来源扫描 | 先核对帖子与来源映射 | 增加分批扫描 |
| 没有外部失败告警 | 人工检查 `journalctl` 和 `app.log` | 阶段 4 接入监控告警 |
| 没有手动 dry-run | 只能做只读盘点和自动化测试 | 后续增加受控管理入口 |
| SQLite 在线备份依赖 `.backup` | 备份后执行完整性检查 | 阶段 4 做恢复演练 |
