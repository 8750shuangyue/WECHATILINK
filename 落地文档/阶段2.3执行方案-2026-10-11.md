# 阶段 2.3 执行方案（真实知识导入与召回指标）

> 制定日期：2026-10-11
> 定位：阶段 2「RAG 可观测性与召回指标」的收口子项，也是阶段 2 唯一尚未闭环的问题
> 关联清单：[阶段 2.3 真实知识导入清单](阶段2.3真实知识导入清单-2026-10-11.md)
> 关联问题：`M-07`（P1，`expectedSourceIds` 未映射到真实来源，`Recall@K` 与引用命中率不可计算）
> 状态：已按第五节顺序执行完成（2026-10-13，本地与生产均已闭环）

## 一、一句话定位

阶段 2.3 要回答一个之前一直没有数据支撑的问题：**线上知识库到底有没有真的被检索到、检索到的是不是我们想让它命中的那份资料。**

它做三件事：把真实业务知识导入线上公共知识库替换测试种子、把正式题库的 `expectedSourceIds` 映射到真实来源、用同一份 40 题复测并算出 `Recall@K` 与引用命中率。

### 2.2 前后依赖

- **它的前置已经全部就位**：
  - 2.1 检索接线已完成，`/api/ai/chat/stream` 与 `/api/care/qa` 已按真实 `userId + conversationId` 检索公共知识库。
  - 2.2 受控只读召回明细接口已完成，评测侧可以通过 `GET /api/internal/rag/retrievals/{traceId}` 拿到「这一问命中了哪些 `sourceId`」。
  - 知识导入接口已具备 `sourceId` 稳定标识、`dryRun` 与按来源整体替换能力。
- **它是阶段 3.4 的前置**：3.4 要做关键词 + 向量混合召回和重排，必须有 2.3 产出的 `Recall@K` 基线，否则无法判断「换了检索策略到底是变好还是变坏」。
- **它是阶段 2 的验收闸门**：2.1、2.2 都已部署，2.3 不闭环，阶段 2 就不能整体验收，也不能进入阶段 3 的检索质量增强。

## 三、为什么这么做

### 3.1 现状：评测成绩漂亮，但和真实知识无关

第一版基线质量通过率 `90.38%`，P0 复测与阶段 0 复测都是 `98.08%`，生产复测 `100%`。但这个成绩有两个结构性空洞：

1. **线上公共知识库只有测试种子**：目前公共向量只有 `post_1`（内容 `dadad`）和 `post_2`（内容 `最近有点挑食`），没有任何真实业务知识。也就是说，模型答对绿植、宠物的问题，靠的是它自己的模型知识，而不是我们导入的资料。
2. **`expectedSourceIds` 全为空数组**：正式题库 40 题的 `expectedSourceIds` 目前都是 `[]`，评分器 [EvalScorer.java](../../TEST/src/test/java/com/example/demo/eval/EvalScorer.java) 的 `sourceRecall()` 只在 `expectedSourceIds` 非空且 `retrievalStatus == "available"` 时才计算，因此召回指标根本算不出来。

### 3.2 不做的代价

- 无法证明「RAG 检索在线上真的生效」，也无法区分「模型答对」和「知识库答对」。一旦模型知识覆盖不到的细分问题出现，就没有兜底证据。
- 阶段 2 的验收项「`Recall@K` 和引用指标有可复现数据」永远无法满足，阶段 2 挂着不闭环。
- 阶段 3.4 的混合召回、重排、上下文压缩失去对照基线，优化效果无从衡量。
- 文档里仍会保留过时口径（见 4.6），对外沟通时容易把「模型知识」误当作「知识库能力」。

### 3.3 为什么现在做

阶段 3.2 的数据治理刚完成首次验收（重复向量 `76 -> 0`、对话向量 `202 -> 126`、公共向量保持 `2`、门禁 `21/21 PASS`），公共向量数量正好处在干净、可追溯的起点。此时导入真实知识、替换两个测试种子，向量数量的变化最清晰，也最容易校验「公共向量来源只剩真实 `sourceId`」。

## 五、怎么做（分步执行）

### 第一步：评审导入清单并拍板三个待定项

以 [阶段 2.3 真实知识导入清单](阶段2.3真实知识导入清单-2026-10-11.md) 为评审对象，重点确认：

- 主题划分与 `sourceId` 命名（绿植 `kb_plant_*` 7 篇、宠物 `kb_pet_*` 12 篇，平台 `kb_platform_*` 1 篇可选）。
- 每道题的 `expectedSourceIds` 映射（单一来源还是 1 至 2 个来源）。
- 三个待拍板点：B1 平台规则篇是否单建、每篇篇幅与块数目标、真实知识的资料来源与授权方式。

### 第二步：编写知识文档

- 存放于仓库 `knowledge/` 目录，文件名用 `sourceId`（如 `kb_plant_watering.md`），便于和向量来源一一对应。
- 单篇控制在 500 至 1500 字，对应 1 至 3 个块；同一主题内容集中，不要把不同主题塞进同一个 `sourceId`。
- 每篇必须写清「必须包含的事实」和「禁止出现的错误结论」（清单第三列、第四列），这两列直接决定题库的 `expectedFacts` / `forbiddenClaims` 能不能被资料支撑。
- 内容红线：医疗/兽医内容必须给就医边界，不得给精确到毫克的自行用药剂量；来源要有权威依据，不整段搬运受版权保护资料。

### 第三步：逐篇 `dryRun` 校验

对每篇文档调用（`dryRun=true` 不写库）：

```bash
curl -s -X POST "http://127.0.0.1:8080/api/kb/upload" \
  -b "cookie.txt" -F "file=@knowledge/kb_plant_watering.md" \
  -F "sourceId=kb_plant_watering" -F "dryRun=true"
```

核对返回的 `count`、`chars`、`sourceId` 是否符合预期（块数在 1 至 3）。`chars` 是 `normalizeText` 把 CRLF 归一为 LF 之后的字符数，比文件本身按 CRLF 计算的字数少一个换行符数量；逐篇实测值见 [`knowledge/README.md`](../../knowledge/README.md) 第一节表格。若单段超过 `500` 字，注意分块器按段落累加、**不会切开单段**，需要人工把长段拆成多段。

### 第四步：正式入库并记录公共向量数量

去掉 `dryRun` 正式入库，每篇记录公共向量数量变化：

```bash
curl -s -X POST "http://127.0.0.1:8080/api/kb/upload" \
  -b "cookie.txt" -F "file=@knowledge/kb_plant_watering.md" \
  -F "sourceId=kb_plant_watering"
curl -s -b "cookie.txt" "http://127.0.0.1:8080/api/kb/list"
```

入库按 `sourceId` 整体替换（`replaceDocument`），重复导入同一 `sourceId` 不会追加，只会替换，因此可安全重跑。

### 第五步：删除测试种子 `post_1`、`post_2`

```bash
curl -s -X DELETE -b "cookie.txt" "http://127.0.0.1:8080/api/kb/post_1"
curl -s -X DELETE -b "cookie.txt" "http://127.0.0.1:8080/api/kb/post_2"
curl -s -b "cookie.txt" "http://127.0.0.1:8080/api/kb/list"
```

确认公共来源只剩真实 `sourceId`，公共向量数量 = 各真实文档块数之和。

### 第六步：更新题库 `expectedSourceIds` 并修过时口径

- 按清单第四节的映射表，更新 `TEST/eval/ai-eval-v1.jsonl` 各行 `expectedSourceIds`（`path: stream` 且检索可用的题才填；`path: tools` 的题保持空数组）。
- 修正两处过时口径（阶段 2.2 之后已失真）：
  - [TEST/README.md](../../TEST/README.md) 中「生产接口未返回内部检索明细，`sourceRecall` 保持为空」的描述。
  - [EvalReportWriter.java](../../TEST/src/test/java/com/example/demo/eval/EvalReportWriter.java:230) 第 230 至 231 行同样的结论。
  实际从阶段 2.2 起，`chatStream` 已可通过 `rag-trace` 事件拿到 `traceId` 并查询召回明细，`sourceRecall` 在 `expectedSourceIds` 非空时可计算。

### 第七步：打开受控观测、40 题复测

- 记录本次配置版本：`topK=5`、`similarity-threshold=0.5`、`CHUNK_LENGTH=500`、Embedding 模型、阈值与题库文件哈希。
- 打开 `app.rag-observability.enabled=true`，把评测账号加入 `app.rag-observability.allowed-users` 白名单。
- 先跑 12 题冒烟，再跑 40 题正式题库：

```bash
mvn -B -f TEST\pom.xml test
```

真实 API 需要 `AI_EVAL_ENABLED=true` 与相关环境变量。评测客户端对 `stream` 题通过 SSE `rag-trace` 事件取 `traceId`、再查召回明细计算 `sourceRecall`；`tools` 题的 `retrievalStatus` 恒为 `not_applicable`，不计入召回。
- 输出 `Recall@K`、引用命中率，必要时增加 Groundedness 口径；保存原始 JSONL 与计算口径，确保可离线重算（`AI_EVAL_REPLAY_FILE` + `-Dtest=EvalReportRegeneratorTest`）。

## 六、验收标准

1. 线上公共知识库只含真实 `sourceId`，无 `post_1`、`post_2`，公共向量数量与各文档块数之和一致。
2. 正式题库 `expectedSourceIds` 已映射到真实来源，`path: stream` 的题不再全为空数组。
3. `Recall@K` 和引用命中率有可复现数据（附原始 JSONL、配置版本、题库哈希），不使用人工猜测值。
4. 质量通过率、事实覆盖、工具成功率、记忆 `4/4` 不低于阶段 1 生产复测基线（当前为 `100%`）。
5. 内部观测接口未登录、越权或白名单外无法访问。
6. 评测报告不再出现「生产接口未返回内部检索明细」的过时表述。

## 七、重要性

**这是「知识库是否真的被用上」的唯一量化证据。**

- 没有它，阶段 2 挂在「真实知识未导入」上无法验收，前面 2.1、2.2 的投入没有闭环。
- 它是阶段 3.4 混合召回与重排的前置基线：没有 `Recall@K` 起点，就无法判断新检索策略是否真的提升了召回。
- 它把线上从「只有 `dadad`、`最近有点挑食` 两个测试种子」变成「有真实、可追溯、可分块管理的业务知识」，是产品可用性的实质一步。

## 八、风险与回滚

| 风险 | 缓解 |
| --- | --- |
| 误删真实向量 | 入库与删除都用 `sourceId` 整体替换，先 `dryRun` 校验再正式写；删除前记录公共向量数量 |
| 分块过大导致单块超限 | `dryRun` 阶段核对块数与字数，超长段落先人工拆分 |
| 题库映射错误导致 `sourceRecall` 虚高/虚低 | 映射表逐题评审；复测保留原始 JSONL 可离线重算 |
| 评测账号或观测开关误配 | 白名单化，默认关闭；评测结束确认开关状态 |
